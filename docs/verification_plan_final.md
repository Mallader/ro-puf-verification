# `puf_core` Verification Plan

## 1. Назначение документа

Целью верификации является проверка модуля `puf_core.sv`. Проверка осуществляется на основании документа `puf_specification.md`. План верификации определяет область, стратегию и средства проверки требований puf_core, устанавливает трассировку требований к сценариям и механизмам проверки, а также задаёт основу для оценки полноты верификации. Результатом верификации является подтверждённое выполнение запланированных проверок, отсутствие нерешённых критических ошибок и достижение согласованных критериев покрытия.

## 2. Объект и уровень верификации

### 2.1. DUT: `puf_core`

Внешний интерфейс DUT:

- `clk27`;
- `rst_n`;
- `start`;
- `challenge`;
- `busy`;
- `ready`;
- `response`;
- `debug_count_a`;
- `debug_count_b`.

Все подмодули, инстанцированные внутри `puf_core`, включая `ro_array`, `challenge_mapper`, `ro_pair_measure`, `puf_fsm`, `response_builder`, `ring_oscillator`, `gate_timer`, `ro_counter`, `snapshot` и `cdc_sync`, являются частью DUT. 

### 2.2. Уровень верификации: block-level functional verification

## 3. Область верификации

### 3.1. Функции в области верификации

* `reset`;
* приём start;
* фиксация challenge;
* поведение busy и ready;
* формирование многобитного response;
* выбор пар RO;
* обработка равенства счётчиков;
* debug-счётчики;
* повторные операции;
* corner cases параметров;
* latency и timeout.

### 3.2. Функции за пределами верификации

* `puf_peripheral`;
* `bus protocol`;
* `RAL`;
* программное обеспечение;
* `UART`;
* физические uniqueness и reliability;
* влияние температуры и напряжения;
* синтез и сохранение физических RO.

## 4. Стратегия верификации

1. Внешний интерфейс `puf_core` используется для основных проверок.
2. Для RTL-симуляции применяется управляемая модель частот RO: RO заменяются осцилляторами с заданной частотой.
3. Результат `response` предсказывается независимой референсной моделью.
4. Протокольные свойства проверяются с помощью monitor и assertions.
5. Функциональное покрытие используется для оценки полноты сценариев.
6. Операции контролируются `timeout`-механизмом: при выходе выполнения симуляции за предустановленные временные рамки симуляция будет завершена с соответствующим уведомлением.
7. Внутренние сигналы используются только для дополнительных white-box-проверок.

### 6.3. Профили симуляционной модели RO

Профиль RO является конфигурацией testbench, а не параметрической конфигурацией DUT.

- `RO-PROFILE-NORMAL` — воспроизводимые различающиеся частоты; используется в большинстве сценариев.
- `RO-PROFILE-TIE-LAST` — одинаковые частоты у пары, формирующей последний response-бит; используется в `SCN-RSP-002`.
- `RO-PROFILE-CLOSE` — небольшая разность частот; используется для проверки tolerance debug-счётчиков и устойчивости предсказания.
- `RO-PROFILE-STOPPED` — один выбранный RO остановлен; используется только в `SCN-LAT-002`.
- `RO-PROFILE-COUNTER-BOUNDARY` — частоты подобраны для `CFG-COUNTER-BOUNDARY` без переполнения.

Все базовые профили должны быть детерминированными. Случайный jitter добавляется только после получения стабильной воспроизводимой регрессии.

## 7. Coverage goals

Functional coverage подтверждает, что запланированные ситуации возникли, но не определяет pass/fail. Правильность реакции DUT проверяется checker, reference model, scoreboard и SVA.

### 7.1. Обязательные объекты покрытия

- `COV-RST-PHASE`: reset в idle после reset, reset в idle при сохранённом `ready`, reset во время `busy`.
- `COV-CMD-TYPE`: принятая команда, однотактный `start` во время `busy`, повторный приём удерживаемого `start` после завершения операции.
- `COV-PAIR`: значения `ro_index_a`, `ro_index_b` и cross разрешённых пар; комбинации `ro_index_a == ro_index_b` считаются illegal.
- `COV-COMPARE-RESULT`: `count_a > count_b`, `count_a < count_b`, `count_a == count_b`.
- `COV-RESPONSE-BIT`: значения 0 и 1 для каждого `bit_index`; cross `bit_index × response_bit`.
- `COV-READY-LIFECYCLE`: установка `ready`, хранение `ready`, сброс новой командой, сброс через reset.
- `COV-LATENCY`: штатная latency, увеличенная штатная latency и ожидаемый timeout.
- `COV-CONFIG`: хотя бы один успешный запуск каждой обязательной `CFG-*`.

### 7.2. Целевые значения

- 100% требований связаны хотя бы с одним сценарием или статической проверкой.
- 100% обязательных динамических сценариев выполнены.
- 100% обязательных functional coverage bins и запланированных crosses покрыты либо имеют документированный waiver.
- 100% достижимых состояний `puf_fsm` и штатных переходов между ними покрыты.
- Каждый непокрытый исполняемый участок RTL проанализирован; необъяснённый непокрытый код не допускается.
- Illegal и ignore bins, а также code-coverage exclusions должны иметь письменное обоснование.

Жёсткий общий процент line/toggle coverage заранее не задаётся: итог оценивается по отсутствию необъяснённых пробелов, а не только по агрегированному числу.

## 8. Критерии pass/fail

### 8.1. Обычный тест

Обычный тест считается пройденным, если одновременно выполнены условия:

- отсутствуют `UVM_ERROR` и `UVM_FATAL`;
- отсутствует неожиданный timeout;
- scoreboard не обнаружил несовпадений;
- не произошло ни одного assertion failure;
- число принятых команд совпадает с числом ожидаемых результатов с учётом reset и отклонённых команд;
- нет лишних событий `ready`;
- к завершению теста нет незаконченных ожидаемых операций;
- все проверки, обязательные для данного сценария, действительно были активированы.

### 8.2. Expected-timeout test

`SCN-LAT-002` считается пройденным, если:

- использован `RO-PROFILE-STOPPED`;
- выбранный остановленный RO действительно входит в одну из измеряемых пар;
- `ready` не появился до установленного лимита;
- watchdog классифицировал timeout как ожидаемый;
- monitor не сформировал лишнюю response-транзакцию;
- симуляция завершилась контролируемо без неожиданного `UVM_FATAL`.

Обычный timeout в любом другом сценарии является ошибкой.

### 8.3. Регрессия

Регрессия считается пройденной, если:

- пройдены все обязательные тесты и конфигурации;
- отсутствуют неожиданные scoreboard mismatch и assertion failures;
- ожидаемые timeout-сценарии отделены от зависаний;
- достигнуты coverage goals либо оформлены согласованные waivers;
- результаты каждого запуска воспроизводимы по имени теста, seed, конфигурации DUT и профилю RO.

## 9. Критерии завершения block-level верификации

Этап верификации `puf_core` считается завершённым, когда:

1. `puf_specification.md` и данный verification plan согласованы и не содержат открытых блокирующих неоднозначностей.
2. 100% требований имеют трассировку к сценарию, статической проверке или обоснованному исключению.
3. Реализованы и выполнены все обязательные динамические сценарии.
4. Выполнены все обязательные параметрические конфигурации.
5. Достигнуты coverage goals или для каждого исключения оформлен waiver.
6. Открытых критических и блокирующих дефектов нет.
7. Все ошибки меньшей серьёзности либо исправлены, либо документированы с принятым решением.
8. Нет необъяснённых scoreboard mismatch, assertion failure, timeout или потерянных операций.
9. Регрессия воспроизводима и сохраняет test name, seed, параметры DUT и профиль RO.
10. Физические свойства PUF — uniqueness, reliability, uniformity, влияние температуры и напряжения — не объявляются проверенными по результатам RTL-симуляции.

## 10. Итоговая трассировка

- `VP-RST` → `SCN-RST-001`–`SCN-RST-003` → `CFG-SIM-BASE`, `CFG-RTL-DEFAULT` → `COV-RST-PHASE`.
- `VP-CMD` → `SCN-CMD-001`–`SCN-CMD-003`, `SCN-CHL-001` → `CFG-SIM-BASE` → `COV-CMD-TYPE`.
- `VP-OP` → `SCN-OP-001`–`SCN-OP-003` → `CFG-SIM-BASE`, `CFG-RTL-DEFAULT`, `CFG-RESPONSE-MIN`, `CFG-SETTLE-ZERO` → `COV-READY-LIFECYCLE`.
- `VP-RSP` → `SCN-RSP-001`–`SCN-RSP-003` → все функциональные `CFG-*` → `COV-PAIR`, `COV-COMPARE-RESULT`, `COV-RESPONSE-BIT`.
- `VP-DBG` → `SCN-DBG-001`, `SCN-OP-002` → `CFG-SIM-BASE`, `CFG-RESPONSE-MIN`, `CFG-COUNTER-BOUNDARY` → `COV-COMPARE-RESULT`.
- `VP-PAR` → матрица `CFG-*` и будущие static parameter checks → `COV-CONFIG`.
- `VP-LAT` → `SCN-LAT-001`, `SCN-LAT-002` → `CFG-SIM-BASE`, `CFG-RTL-DEFAULT`, `CFG-RESPONSE-MIN`, `CFG-SETTLE-ZERO` → `COV-LATENCY`.

Каждый сценарий должен ссылаться хотя бы на одно требование. Каждое требование должно быть покрыто сценарием, статической проверкой или явно документированным исключением.
