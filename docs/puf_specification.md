# puf\_core Specification

## 1\. Назначение

puf\_core формирует многобитный PUF-response шириной RESPONSE\_BITS битов в соответствии с получаемым им входным воздействием (challenge) шириной CHALLENGE\_WIDTH бит. Помимо вышеперечисленных сигналов, puf\_core также получает на вход тактовый сигнал clk27, асинхронный сигнал сброса rst\_n (при rst\_n == 0 происходит сброс) и сигнал start, который является однотактным импульсом запуска. Выходные сигналы: busy сообщает, что модуль выполняет операцию и не готов принять новую команду, ready сообщает, что формирование response завершено и результат доступен, debug\_count\_a и debug\_count\_b значения счетчиков для двух измеренных кольцевых осцилляторов. Операцией называется процесс формирования полного многобитного response, начинающийся на фронте приёма команды и заканчивающийся установкой ready

## 4\. Поведение при reset

Сигнал rst\_n является асинхронным сигналом сброса, активным низким уровнем. Активация reset отменяет выполняющуюся операцию, очищает внешние результаты и переводит DUT в состояние ожидания новой команды.

### REQ-RST-001

Сигнал rst\_n должен быть активным низким уровнем сигналом reset.
Переход rst\_n из 1 в 0 должен переводить последовательную логику puf\_core в reset-состояние без ожидания положительного фронта clk27.

### REQ-RST-002

Пока rst\_n == 0, выход busy должен иметь значение 0.

### REQ-RST-003

Пока rst\_n == 0, выход ready должен иметь значение 0.

### REQ-RST-004

Пока rst\_n == 0, выход response должен иметь значение 0.

### REQ-RST-005

При активном reset выходы debug\_count\_a и debug\_count\_b
должны иметь значение 0.

### REQ-RST-006

Операция, выполнявшаяся в момент активации reset, должна считаться отменённой и не должна возобновляться после снятия reset.

### REQ-RST-007

Операция, прерванная reset, не должна приводить к последующей
установке ready после снятия reset без приёма новой команды.

### REQ-RST-008

После снятия reset DUT должен оставаться в состоянии ожидания
до приёма новой команды start со значениями:



* busy == 1'b0;
* ready == 1'b0;
* response == '0;
* debug\_count\_a == '0;
* debug\_count\_b == '0.

### REQ-RST-009

При rst\_n == 0 вход start не должен запускать новую операцию.

### REQ-RST-010

Если после снятия reset сигнал start имеет значение 1 на положительном фронте clk27, DUT должен принять новую команду на этом фронте. Если start был снят до первого положительного фронта clk27 после reset, операция не должна начинаться.

|Выход|Значение при rst\_n == 0|Состояние после снятия reset|
|-|-:|-|
|busy|0|Если start == 1 на положительном фронте clk27, когда  FSM находится в STATE\_IDLE, команда принимается. После этого фронта  FSM переходит в STATE\_CLEAR\_RESPONSE, и busy становится равным 1.|
|ready|0|остаётся равным 0 до завершения новой операции|
|response|0|Остаётся равным 0 до сохранения результатов новой операции; действителен при ready == 1|
|debug\_count\_a|0|После reset выход сохраняет значение 0 до первого импульса response\_store новой операции. При каждом response\_store в него записывается счётчик текущей измеренной пары.|
|debug\_count\_b|0|После reset выход сохраняет значение 0 до первого импульса response\_store новой операции. При каждом response\_store в него записывается счётчик текущей измеренной пары.|

## 5\. Приём команды и фиксация `challenge`

### 5.1. Событие приёма команды

Команда принимается на положительном фронте `clk27`, на котором одновременно выполняются следующие условия:

* `rst\_n == 1`;
* `start == 1`;
* `busy == 0`.

Значение `start`, наблюдаемое при `busy == 1`, не считается принятой командой.

### 5.2. Требования к `start`

### REQ-CMD-001

DUT должен принимать новую команду на положительном фронте `clk27`, если на этом фронте `rst\_n == 1`, `start == 1` и `busy == 0`.

### REQ-CMD-002

Для формирования корректного запроса источник команды должен удерживать сигнал `start` высоким в течение одного такта `clk27`.

### REQ-CMD-003

Сигнал `start`, наблюдаемый на положительном фронте `clk27` при `busy == 1`, не должен приниматься как новая команда и не должен перезапускать текущую операцию.

### REQ-CMD-004

Однотактный импульс `start`, полностью пришедший во время `busy == 1`, не должен сохраняться DUT для последующего запуска операции.

### REQ-CMD-005

Если сигнал `start` остаётся равным `1` до положительного фронта `clk27`, на котором `busy == 0`, DUT должен принять его как новую команду. Это поведение является следствием чувствительности интерфейса к уровню `start`, а не к его фронту.

### 5.3. Требования к `challenge`

### REQ-CHL-001

На положительном фронте `clk27`, на котором принимается команда, DUT должен зафиксировать текущее значение входа `challenge`.

### REQ-CHL-002

Изменения входа `challenge` после приёма команды не должны изменять выбор пар RO и формируемый `response` текущей операции.

### REQ-CHL-003

Если `start == 1` при `busy == 1`, значение зафиксированного `challenge` текущей операции не должно перезаписываться.

### 5.4. Сценарии приёма команды

|Сценарий|Принимается ли команда?|Какой `challenge` фиксируется?|Влияние на операцию|
|-|-|-|-|
|`start == 1`, `busy == 0` в течение одного такта|Да, на положительном фронте `clk27`|Текущее значение входа `challenge`|Начинается новая операция|
|Входной `challenge` изменяется после приёма команды|Новая команда не принимается только из-за изменения `challenge`|Ранее зафиксированное значение сохраняется|Текущая операция не изменяется|
|Однотактный `start` приходит при `busy == 1`|Нет|Зафиксированный `challenge` не изменяется|Текущая операция продолжается; запрос не помещается в очередь|
|`start` удерживается высоким несколько тактов с начала операции|Первая команда принимается при `busy == 0`; во время `busy == 1` новые команды не принимаются|Для первой операции фиксируется значение на первом допустимом фронте|Если `start` останется высоким после возвращения `busy` в `0`, будет принята ещё одна команда|
|`start` остаётся равным `1` после завершения операции|Да, на первом положительном фронте при `busy == 0`|Значение `challenge`, присутствующее на этом фронте|Начинается новая операция|
|Новое значение `challenge` присутствует при допустимом `start`|Да|Новое значение, присутствующее на фронте приёма команды|Начинается операция с новым `challenge`|



## 6\. Жизненный цикл операции: start, busy и ready

### 6.1. Соответствие текущей реализации FSM

|Состояние|`busy`|`done` / `sequence\_done`|Условие выхода|
|-|-:|-:|-|
|`STATE\_IDLE`|0|0|start == 1|
|`STATE\_CLEAR\_RESPONSE`|1|0|если RO\_SETTLE\_CYCLES == 0, то переход в STATE\_START\_PAIR; иначе - STATE\_SETTLE;|
|`STATE\_SETTLE`|1|0|settle\_count == SETTLE\_LAST\_COUNT|
|`STATE\_START\_PAIR`|1|0|безусловный переход в `STATE\_WAIT\_PAIR`|
|`STATE\_WAIT\_PAIR`|1|0|pair\_done == 1|
|`STATE\_STORE\_RESULT`|1|0|если bit\_index == LAST\_BIT\_INDEX, то переход в STATE\_DONE; иначе если RO\_SETTLE\_CYCLES == 0 - STATE\_START\_PAIR; иначе - STATE\_SETTLE;|
|`STATE\_DONE`|1|1|безусловный переход в `STATE\_IDLE`|

| Событие                   | Состояние до фронта  | Состояние после фронта      | `start` | `busy` после фронта | `ready` после фронта |
| ------------------------- | -------------------- | --------------------------- | ------: | ------------------: | -------------------: |
| До первой команды         | `STATE_IDLE`         | —                           |       0 |                   0 |              0 или 1 |
| `E0`: приём команды       | `STATE_IDLE`         | `STATE_CLEAR_RESPONSE`      |       1 |                   1 |                    0 |
| Внутреннее выполнение     | рабочее состояние    | следующее рабочее состояние |       0 |                   1 |                    0 |
| `ED`: вход в завершение   | `STATE_STORE_RESULT` | `STATE_DONE`                |       0 |                   1 |                    0 |
| `EF`: завершение операции | `STATE_DONE`         | `STATE_IDLE`                | 0 или 1 |                   0 |                    1 |
| Ожидание                  | `STATE_IDLE`         | `STATE_IDLE`                |       0 |                   0 |                    1 |
| `EN`: новая команда       | `STATE_IDLE`         | `STATE_CLEAR_RESPONSE`      |       1 |                   1 |                    0 |


Е0 - фронт приёма команды, EF - фронт выхода из STATE\_DONE, ED — фронт перехода STATE_STORE_RESULT → STATE_DONE.

### 6.2. Требования к операции

#### REQ-OP-001

Операция должна считаться начатой на положительном фронте
`clk27`, на котором DUT принимает новую команду.

#### REQ-OP-002

С момента после фронта приёма команды и до завершения операции
DUT должен находиться в состоянии выполнения операции:
`busy == 1` и `ready == 0`.

#### REQ-OP-003

Операция должна считаться завершённой на положительном фронте
`clk27`, после которого `busy` принимает значение `0`, а `ready`
принимает значение `1`.

#### REQ-OP-004

После завершения операции DUT должен поддерживать возможность
приёма следующей команды без дополнительной активации reset. 

### 6.3. Требования к `busy`

#### REQ-BUSY-001

Сигнал busy в STATE_IDLE должен принимать значение 0.

#### REQ-BUSY-002

Значение busy во всех остальных состояниях (включая STATE_DONE) - 1.

#### REQ-BUSY-003

Если команда принята на положительном фронте `clk27`, в тактовом интервале непосредственно после этого же фронта выход `busy` должен иметь значение `1`.

#### REQ-BUSY-004

busy принимает значение 0, когда FSM переходит в состояние STATE_IDLE. 


### 6.4. Требования к `ready`

#### REQ-RDY-001

На положительном фронте `clk27`, на котором принимается новая команда, DUT должен установить `ready` в `0`. После этого фронта `ready` должен иметь значение `0`.

#### REQ-RDY-002

Значение ready во время выполнения операции - 0.

#### REQ-RDY-003

На положительном фронте `clk27`, на котором FSM переходит из `STATE_DONE` в `STATE_IDLE`, DUT должен установить `ready` в `1`.

#### REQ-RDY-004

ready == 1 сохраняется до прихода новой команды или активации reset.

#### REQ-RDY-005

Невозможна ситуация, когда busy == 1 && ready == 1.

## 7. Семантика `response`, debug-счётчиков и tie

### 7.1. Последовательность обновления выходных данных

| Интервал после фронта | Состояние после фронта                | `busy` | `ready` | `response`                       | Debug-счётчики                               | Данные действительны     |
| --------------------- | ------------------------------------- | -----: | ------: | -------------------------------- | -------------------------------------------- | ------------------------ |
| До A                  | `STATE_IDLE`                          |      0 | 0 или 1 | предыдущий результат             | последняя пара предыдущей операции либо нули | только если `ready == 1` |
| После A               | `STATE_CLEAR_RESPONSE`                |      1 |       0 | предыдущий результат             | предыдущая пара либо нули                    | нет                      |
| После C               | `STATE_SETTLE` или `STATE_START_PAIR` |      1 |       0 | `'0`                             | `'0`                                         | нет                      |
| После S₀              | `STATE_SETTLE` или `STATE_START_PAIR` |      1 |       0 | записан бит 0                    | счётчики пары для бита 0                     | нет                      |
| После Sᵢ              | `STATE_SETTLE` или `STATE_START_PAIR` |      1 |       0 | записаны биты `0…i`              | счётчики пары для бита `i`                   | нет                      |
| После Slast           | `STATE_DONE`                          |      1 |       0 | полный новый `response`          | счётчики последнего бита                     | нет                      |
| После R               | `STATE_IDLE`                          |      0 |       1 | действительный полный `response` | счётчики последнего бита                     | да                       |

Обозначения:
- A — фронт приёма команды;
- C — первый положительный фронт после A, на котором выполняется очистка;
- Sᵢ — фронт сохранения response-бита с индексом `i`;
- Slast — фронт сохранения последнего response-бита;
- R — фронт установки `ready`.

### 7.2. Требования к `response`

#### REQ-RSP-001
`response` должен быть очищен в `0` на первом положительном фронте `clk27` после фронта приёма новой команды.
#### REQ-RSP-002
Между фронтом приёма новой команды и следующим положительным фронтом `clk27` значение `response` не должно изменяться.
#### REQ-RSP-003
На каждом положительном фронте `clk27`, на котором `response_store == 1`, должен обновляться только бит `response[bit_index]`. Все остальные биты `response` должны сохранять предыдущие значения.
#### REQ-RSP-004
Биты записываются в порядке от индекса 0 до RESPONSE_BITS-1.
#### REQ-RSP-005
Полный результат считается действительным, когда ready == 1.
#### REQ-RSP-006
После установки `ready` значение полного `response` должно сохраняться до активации reset либо до положительного фронта `clk27`, на котором выполняется очистка `response` в начале следующей операции.
#### REQ-RSP-007
Правило для response[bit_index]:
| Сравнение счётчиков |	 Значение response-бита |
| --------------------| ----------------------: |
|count_a > count_b|	1 |
|count_a < count_b|	0 |
|count_a == count_b|	0|

### 7.3. Требования к debug-счётчикам

#### REQ-DBG-001
Очистка debug-счётчиков выполняется на первом положительном фронте, после фронта приема команды.
#### REQ-DBG-002
Обновление debug-счётчиков выполняется при каждом response_store.
#### REQ-DBG-003
После каждого `response_store` значения `debug_count_a` и `debug_count_b` должны соответствовать паре RO, использованной для формирования только что сохранённого бита `response[bit_index]`.
#### REQ-DBG-004
Значения debug-счётчиков могут изменяться во время busy == 1.
#### REQ-DBG-005
После установки ready debug-счётчики описывают пару, использованную для формирования последнего response-бита.
#### REQ-DBG-006
Значения debug-счётчиков сохраняются до следующего обновления, очистки или reset.

### 7.4. Пример формирования многобитного response

Пусть RESPONSE_BITS = 4, тогда:

| `bit_index` | `count_a` | `count_b` | pair_tie | Записанный бит | `response` после сохранения | Debug-счётчики после сохранения |
| ----------: | --------: | --------: | --: | -------------: | --------------------------- | ------------------------------- |
| 0 | 10 | 11 | 0 | 0 | 0000 | 10, 11 |
| 1 | 15 | 12 | 0 | 1 | 0010 | 15, 12 |
| 2 | 13 | 13 | 1 | 0 | 0010 | 13, 13 |
| 3 | 17 | 11 | 0 | 1 | 1010 | 17, 11 |

### 8.2. Таблица corner cases

| Конфигурация                          | Допустима? | Фактическое поведение | Риск или ограничение |
| ------------------------------------- | ---------: | --------------------- | -------------------- |
| `NUM_RO == 1`                         | Нет | Оба индекса равны нулю, выбирается один и тот же RO | Невозможно сформировать пару различных RO; конфигурация нарушает назначение DUT |
| `NUM_RO == 2`                         | Да | Используется одна физическая пара RO, возможно в двух порядках: `RO0/RO1` и `RO1/RO0` | Разные response-биты сильно коррелированы и не представляют независимые сравнения |
| `NUM_RO`, не равный степени двойки    | Да | Распределение индексов получается неравномерным | Это не ошибка функциональной логики, но потенциальный источник смещения при исследовании PUF |
| `RESPONSE_BITS == 1`                  | Да | response шириной в 1 бит | Рассчитанный response содержит только один бит и обладает крайне ограниченной энтропией |
| `RO_SETTLE_CYCLES == 0`               | Да | STATE_SETTLE обходится | Измерение начинается без отдельной стабилизационной паузы |
| `RO_SETTLE_CYCLES == 1`               | Да | DUT проводит один такт в STATE_SETTLE | На стабилизационную паузу предоставляется один такт clk27 |
| `WINDOW_CYCLES == 0`                  | Нет | Из-за усечения WINDOW_CYCLES - 1 до однобитного LAST_COUNT формируется окно длительностью два такта | Значение параметра не соответствует фактической длительности окна |
| `WINDOW_CYCLES == 1`                  | Да | `gate_en` активен в течение одного периода `clk27`. | Окно может оказаться слишком коротким для гарантированного обнаружения его высокого уровня обоими RO-доменами |
| Переполнение `challenge + bit_index`  | Да | При переполнении значение циклически переходит через ноль | DUT не гарантирует, что для разных response-битов будут выбраны разные пары RO  |
| Повторное использование одной пары RO | Да | Повторное использование одной пары RO | Уменьшение числа независимых сравнений, корреляция response-битов и снижение эффективной энтропии response. |
| Переполнение RO-счётчика              | Нет | Счётчик переполняется по модулю 2^COUNTER_WIDTH | Переполнение может изменить не только debug-значение, но и сам response-бит |

### 8.3. Требования к параметрам

#### REQ-PAR-001
`NUM_RO` должен быть не меньше 2. Для равномерного отображения исходных кодов на индексы RO
рекомендуется выбирать `NUM_RO`, равный степени двойки.
#### REQ-PAR-002
RESPONSE_BITS должен быть >=1.
#### REQ-PAR-003
CHALLENGE_WIDTH должен быть >= 2 × INDEX\_WIDTH, где: INDEX\_WIDTH = 1, если NUM\_RO <= 2; INDEX\_WIDTH = $clog2(NUM\_RO), если NUM\_RO > 2.
#### REQ-PAR-004
COUNTER_WIDTH должен быть выбран так, чтобы максимальное
ожидаемое число фронтов любого RO за измерительное окно
не превышало 2^COUNTER_WIDTH - 1. N_edges_max ≈ f_RO_max × T_measure_max, T_measure = WINDOW_CYCLES / f_clk27.
#### REQ-PAR-005
WINDOW_CYCLES должен быть не меньше 1.
#### REQ-PAR-006
Длительность активного уровня измерительного окна должна быть достаточной для его обнаружения в обоих выбранных RO-доменах.
#### REQ-PAR-007
RRO_SETTLE_CYCLES должен быть не меньше 0.
#### REQ-PAR-008
DUT не гарантирует, что для разных response-битов будут выбраны разные пары RO.

### 8.4. Требования к задержке

#### REQ-LAT-001
`L_total` определяется как число периодов `clk27` от фронта
приёма внешней команды до фронта, после которого `ready == 1`.
#### REQ-LAT-002
`L_pair[i]` определяется как число периодов `clk27` от фронта,
на котором `ro_pair_measure` принимает `pair_start` для бита
`i`, до фронта, после которого `pair_done == 1`.
#### REQ-LAT-003
Полная latency определяется выражением:
L_total =
    Σ L_pair[i]
    + N × (S + 3)
    + 2,

где сумма берётся от i = 0 до N - 1,
N = RESPONSE_BITS,
S = RO_SETTLE_CYCLES.
#### REQ-LAT-004
Конечная latency гарантируется только при условии, что оба
выбранных RO продолжают переключаться и обнаруживают начало
и окончание измерительного окна.
#### REQ-LAT-005
Численная верхняя граница latency определяется с учётом
минимально допустимой частоты RO и максимальной задержки CDC.
